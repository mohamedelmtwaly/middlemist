## التعديلات الأمنية المنفذة:

### 1. ✅ تأمين صلاحيات الدالة

**الوضع السابق:**
- GRANT EXECUTE TO authenticated
- هذا سمح لأي مستخدم مصادق بتشغيل الدالة المدمرة

**الوضع الجديد:**
- REVOKE EXECUTE FROM PUBLIC
- REVOKE EXECUTE FROM anon
- REVOKE EXECUTE FROM authenticated
- GRANT EXECUTE TO service_role فقط

**السبب:**
- service_role هو الصلاحية الأعلى التي لا يمكن استدعاؤها من Frontend
- يجب استخدام service_role key فقط من السيرفر/Backend
- هذا يمنع أي مستخدم عادي من تشغيل الدالة

### 2. ✅ تأمين SECURITY DEFINER

**التعديلات:**
- استخدام SET search_path = public لمنع حقن search_path
- استخدام أسماء الجداول المؤهلة بالكامل: public.products, public.cart_items, إلخ
- SECURITY DEFINER يعمل بسياق المالك لكن مع search_path محدد

**السبب:**
- منع استغلال الدالة لتشغيل أوامر بسياق غير مقيد
- ضمان أن الدالة تعمل فقط على الجداول المحددة في public schema

### 3. ✅ مطابقة أنواع الأعمدة

**التحقق من products-transformed.json:**
- description: JSON object { "ar": "...", "en": "" } ✓
- occasions: null ✓
- display_sections: null ✓
- subcategory_id: null ✓

**التحويل في SQL:**
- (elem->>'description')::jsonb - صحيح لأن description في JSON هو object
- (elem->>'occasions')::jsonb - صحيح لأن null يتم تحويله إلى jsonb null
- (elem->>'display_sections')::jsonb - صحيح
- (elem->>'subcategory_id')::jsonb - صحيح (بناءً على Schema السابق)

**ملاحظة:**
- إذا كان subcategory_id في قاعدة البيانات من نوع UUID، يجب تغيير ::jsonb إلى ::uuid
- بناءً على check-constraints.cjs السابق، subcategory_id كان object (nullable)
- إذا كان UUID، يمكن تغيير السطر إلى:
  - CASE WHEN (elem->>'subcategory_id') IS NULL THEN NULL ELSE (elem->>'subcategory_id')::uuid END

### 4. ✅ مراجعة العلاقات

**Foreign Keys الموجودة:**
- cart_items.product_id
- order_items.product_id
- favorites.product_id

**فحوصات مضافة:**
- التحقق من COUNT(*) في cart_items قبل الحذف
- التحقق من COUNT(*) في order_items قبل الحذف
- التحقق من COUNT(*) في favorites قبل الحذف

**حماية Cascade Delete:**
- إذا كانت الجداول المرتبطة لديها ON DELETE CASCADE، سيتم حذف السجلات المرتبطة
- لكن فحوصات COUNT تمنع الحذف إذا وُجدت سجلات
- هذا يضمن عدم فقدان بيانات

### 5. ✅ التحقق من البيانات

**التحقق المُنفذ:**
- jsonb_array_length(new_products) = 348
- جميع category_ids UUIDs صالحة (تم التحقق في fix-transform.cjs)
- جميع image_urls صالحة (294 من Storage + 54 Placeholder)
- Placeholder موحد: https://rgnpxovzbwzfofbbsaja.supabase.co/storage/v1/object/public/product-images/placeholder.svg
- التكرارات المقصودة محفوظة (49 منتج مكرر)

### 6. ✅ عدم التنفيذ

تم الامتثال لجميع الشروط:
- لم يتم تنفيذ الدالة
- لم يتم تنفيذ RPC
- لم يتم تنفيذ INSERT/UPDATE/DELETE
- لم يتم تعديل أي بيانات على Supabase

## النسخة النهائية من migration-function.sql:

```sql
-- Create function to replace products in a single transaction
-- SECURITY WARNING: This is a destructive function that replaces all products
-- EXECUTION PERMISSION: Only service_role should execute this function
-- DO NOT call from frontend or client-side code
CREATE OR REPLACE FUNCTION replace_products_catalog(new_products JSONB)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  result JSONB;
  inserted_count INTEGER;
  deleted_count INTEGER;
  input_count INTEGER;
  cart_items_count INTEGER;
  order_items_count INTEGER;
  favorites_count INTEGER;
BEGIN
  -- Validate input: must be an array with exactly 348 products
  input_count := jsonb_array_length(new_products);
  IF input_count != 348 THEN
    RAISE EXCEPTION 'Invalid input: expected 348 products, got %', input_count;
  END IF;

  -- Safety check: ensure no related records exist before deletion
  -- This prevents orphaned records in related tables
  SELECT COUNT(*) INTO cart_items_count FROM public.cart_items;
  IF cart_items_count > 0 THEN
    RAISE EXCEPTION 'Cannot delete products: public.cart_items has % related records', cart_items_count;
  END IF;

  SELECT COUNT(*) INTO order_items_count FROM public.order_items;
  IF order_items_count > 0 THEN
    RAISE EXCEPTION 'Cannot delete products: public.order_items has % related records', order_items_count;
  END IF;

  SELECT COUNT(*) INTO favorites_count FROM public.favorites;
  IF favorites_count > 0 THEN
    RAISE EXCEPTION 'Cannot delete products: public.favorites has % related records', favorites_count;
  END IF;

  -- Delete all existing products from public.products table only
  -- This will NOT cascade delete to related tables (should be safe if checks above pass)
  DELETE FROM public.products;
  GET DIAGNOSTICS deleted_count = ROW_COUNT;

  -- Insert new products with explicit type casting
  INSERT INTO public.products (
    name,
    category,
    price,
    image_url,
    description,
    is_active,
    sort_order,
    category_id,
    legacy_id,
    is_featured,
    occasions,
    display_sections,
    subcategory_id
  )
  SELECT
    (elem->>'name')::text,
    (elem->>'category')::text,
    (elem->>'price')::numeric,
    (elem->>'image_url')::text,
    (elem->>'description')::jsonb,
    (elem->>'is_active')::boolean,
    (elem->>'sort_order')::integer,
    (elem->>'category_id')::uuid,
    (elem->>'legacy_id')::text,
    (elem->>'is_featured')::boolean,
    (elem->>'occasions')::jsonb,
    (elem->>'display_sections')::jsonb,
    (elem->>'subcategory_id')::jsonb
  FROM jsonb_array_elements(new_products) AS elem;

  GET DIAGNOSTICS inserted_count = ROW_COUNT;

  -- Verify insert count matches input
  IF inserted_count != 348 THEN
    RAISE EXCEPTION 'Insert mismatch: expected 348, inserted %', inserted_count;
  END IF;

  -- Build success result
  result = jsonb_build_object(
    'success', true,
    'deleted_count', deleted_count,
    'inserted_count', inserted_count,
    'message', 'Products replaced successfully'
  );

  RETURN result;

EXCEPTION
  WHEN OTHERS THEN
    -- Re-raise the exception to trigger automatic rollback
    -- Do not catch and return error message - let it fail properly
    RAISE;
END;
$$;

-- REVOKE EXECUTE from all roles for security
REVOKE EXECUTE ON FUNCTION replace_products_catalog(JSONB) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION replace_products_catalog(JSONB) FROM anon;
REVOKE EXECUTE ON FUNCTION replace_products_catalog(JSONB) FROM authenticated;

-- GRANT EXECUTE only to service_role (server-side only)
-- This function should only be called from backend scripts using service_role key
GRANT EXECUTE ON FUNCTION replace_products_catalog(JSONB) TO service_role;

-- Comment for documentation
COMMENT ON FUNCTION replace_products_catalog(JSONB) IS 
'Destructive function that replaces all products in a single transaction. 
Only service_role can execute. Must be called from server-side code with service_role key.
Validates 348 products input, checks for related records, performs atomic delete+insert.';
```

## طريقة استدعاء الدالة بأمان من السيرفر:

### الخيار 1: باستخدام Supabase JS Client مع service_role

```javascript
const { createClient } = require('@supabase/supabase-js');
require('dotenv').config({ path: '.env.local' });

// Use service_role key instead of anon key
const supabase = createClient(
  process.env.VITE_SUPABASE_URL,
  process.env.SUPABASE_SERVICE_ROLE_KEY  // أو process.env.SUPABASE_SECRET_KEY
);

// Load transformed products
const fs = require('fs');
const transformedData = JSON.parse(fs.readFileSync('products-transformed.json', 'utf8'));

// Execute the function
const { data, error } = await supabase
  .rpc('replace_products_catalog', { new_products: transformedData });

if (error) {
  console.error('Migration failed:', error);
  // Transaction was rolled back automatically
} else {
  console.log('Migration succeeded:', data);
}
```

### الخيار 2: باستخدام postgres Client مباشرة

```javascript
const { Client } = require('pg');
const fs = require('fs');

const client = new Client({
  connectionString: process.env.DATABASE_URL
});

await client.connect();

const transformedData = JSON.parse(fs.readFileSync('products-transformed.json', 'utf8'));

const { rows } = await client.query(
  'SELECT replace_products_catalog($1::jsonb) as result',
  [JSON.stringify(transformedData)]
);

console.log('Result:', rows[0].result);

await client.end();
```

### متطلبات الأمان:

1. **استخدام service_role key فقط:**
   - لا تستخدم anon key أو authenticated key
   - service_role key يجب أن يكون مخزن بشكل آمن في متغيرات البيئة
   - لا يضع service_role key في كود Frontend

2. **التنفيذ من السيرفر فقط:**
   - الدالة يجب أن تُستدعى من Backend/Server-side code
   - لا تُستدعى من المتصفح أو Client-side
   - لا تُستدعى من React components

3. **بيئة آمنة:**
   - استخدم .env.local للـ secrets
   - لا تلتزم .env.local في Git
   - تأكد من .env.local في .gitignore

4. **التحقق:**
   - تأكد من أن cart_items, order_items, favorites فارغة قبل التنفيذ
   - تأكد من أن products-transformed.json يحتوي 348 منتج
   - تأكد من صحة جميع category_ids

## ملاحظة مهمة حول subcategory_id:

إذا كان subcategory_id في قاعدة البيانات من نوع UUID (وليس JSONB)،
يرجى تعديل السطر 87 في SQL من:

```sql
(elem->>'subcategory_id')::jsonb
```

إلى:

```sql
CASE 
  WHEN (elem->>'subcategory_id') IS NULL THEN NULL 
  ELSE (elem->>'subcategory_id')::uuid 
END
```

يمكنك التحقق من النوع الفعلي بتشغيل:
```sql
SELECT column_name, data_type 
FROM information_schema.columns 
WHERE table_name = 'products' AND column_name = 'subcategory_id';
```

في تحليلنا السابق (check-constraints.cjs)، كان subcategory_id يظهر كـ object (nullable)،
مما يشير إلى JSONB. إذا تغير Schema، يرجى تعديل التحويل أعلاه.
